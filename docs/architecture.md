# Organic-Interface 架构设计文档

## 第一章：项目架构概述

### 1.1 项目定位

Organic-Interface 是一个多模态自动化 AI CLI 工具，专注于代码领域，采用插件化架构设计，支持多模态场景。项目以"内核稳定 + 外围灵活 + 一切皆可组合"为核心理念，为开发者提供可扩展的智能代理框架。

### 1.2 核心设计理念

Organic-Interface 的架构设计遵循以下核心理念：

- **内核稳定**：底层功能高度稳定、接口规范、可复用，高频操作不依赖 AI 推理
- **外围灵活**：交互层可替换、可扩展、可自定义，支持多种 AI Provider 和策略
- **一切皆可组合**：遵循 Unix/Linux 哲学，模块间通过标准化接口通信，支持管道式组合和流式操作

### 1.3 架构风格

项目采用**三层分离架构**（Three-Layer Separation Architecture），将系统划分为内核层、外围模块化交互层和自定义层。每一层有明确的职责边界和接口规范，层间通过统一的通信协议交互。

```
┌──────────────────────────────────────────────────────────────────┐
│                   自定义层 (Customization)                        │
│   CLI 命令定义 · 任务模板 · Provider 注册 · 配置存储              │
├──────────────────────────────────────────────────────────────────┤
│               外围模块化交互层 (Peripheral / Agent)                │
│   Agent 调度 · 任务编排 · 工作流引擎 · 上下文管理 · 通信 · 注册中心 │
├──────────────────────────────────────────────────────────────────┤
│                      内核层 (Kernel)                              │
│   事件总线 · 生命周期管理 · 插件管理 · 文本输出 · 系统信息         │
└──────────────────────────────────────────────────────────────────┘
```

### 1.4 设计哲学

Organic-Interface 的设计哲学深受 Unix/Linux 哲学影响：

- **Do One Thing Well**：每个模块专注于单一职责
- **Pipeline Composition**：模块间通过管道式组合实现复杂功能
- **Plain Text Protocol**：层间通信使用 JSON/文件/stdin-stdout 等通用格式
- **Extensibility First**：新功能通过插件机制接入，而非修改核心

## 第二章：三层架构详细定义

### 2.1 内核层（Kernel Layer）

#### 职责

提供稳定、可靠、低延迟的底层功能，是整个系统的稳定基石。内核层独立运行，高频操作不依赖 AI 推理，避免延迟和错误。

#### 核心功能清单

| 功能               | 说明                   | 关键特性                         |
| ------------------ | ---------------------- | -------------------------------- |
| 事件总线           | 事件驱动通信机制       | 发布-订阅模式、异步非阻塞、类型安全 |
| 生命周期管理       | 内核状态机管理         | 创建→初始化→启动→运行→停止→错误   |
| 插件管理           | 插件加载和注册         | 动态加载、生命周期钩子、元数据管理 |
| 文本输出服务       | CLI 文本输出           | 样式化输出、表格、列表、Spinner    |
| 系统信息服务       | 系统和运行时信息       | 项目上下文、平台信息、运行时信息   |
| 日志系统           | 统一日志记录和管理     | 分级日志、结构化输出               |

#### 内核层核心组件

| 组件               | 类/接口               | 说明                                                         |
| ------------------ | --------------------- | ------------------------------------------------------------ |
| **Kernel**         | `Kernel`              | 核心运行时，整合所有内核组件，实现 `KernelApi` 接口              |
| **EventBus**       | `EventBus`            | 事件总线，支持 `KernelEvents` 标准事件和自定义事件订阅         |
| **LifecycleManager** | `LifecycleManager`  | 生命周期状态机，管理 `LifecycleState`（CREATED→INITIALIZING→…→STOPPED→ERROR） |
| **PluginManager**  | `PluginManager`       | 插件管理器，负责插件的注册、初始化、查找、卸载                 |
| **TextService**    | `TextService`         | 文本输出服务，支持样式化打印、表格渲染、列表输出、Spinner 动画 |
| **InfoService**    | `InfoService`         | 系统信息服务，提供 `ProjectContext`、`SystemInfo`、`PlatformInfo`、`RuntimeInfo` |

#### 设计原则

- **高度稳定**：内核层 API 一旦发布，向后兼容，低频更新
- **接口规范**：所有内核功能通过标准化接口暴露，隐藏实现细节
- **可复用**：内核功能可被任意外围模块调用，无副作用
- **独立运行**：内核层不依赖外围层，可独立启动和运行

#### 约束

- 高频操作直接在内核层执行，不经过 AI Router 决策
- 内核层不得包含业务逻辑和 AI 推理代码
- 内核层接口变更需经过严格的兼容性评估

### 2.2 外围模块化交互层（Peripheral / Agent Layer）

#### 职责

提供灵活、多样、可自定义的交互能力，是系统的智能决策和任务编排中心。外围层负责 Agent 调度、任务编排、工作流执行、上下文管理和 Agent 间通信。

#### 核心功能清单

| 功能               | 说明                   | 关键特性                               |
| ------------------ | ---------------------- | -------------------------------------- |
| Agent 调度         | 智能任务路由和分发     | 策略驱动、动态调度、优先级队列           |
| 任务编排           | 任务分解和流程控制     | 串行/并行/条件/循环、依赖管理           |
| 工作流引擎         | DAG 工作流定义和执行   | 拓扑排序、节点执行、版本管理             |
| 上下文管理         | 对话上下文和状态管理   | 上下文窗口、消息管理、状态持久化         |
| 编排层             | 复杂任务分解和协同     | 任务分解、Agent 选择、并行执行协调       |
| Agent 注册中心     | Agent 注册和发现       | 能力匹配、心跳检测、健康检查、负载均衡   |
| Agent 通信         | Agent 间消息传递       | 发布-订阅、消息队列、通道管理            |
| 异常处理           | 错误恢复和重试机制     | 自动重试、降级策略                       |

#### Agent 多层架构

外围层采用**并行多层 Agent 架构**，实现复杂任务的智能分解和协同处理：

```
┌─────────────────────────────────────────────────────────┐
│                    编排层 (OrchestrationLayer)            │
│   任务分解 · Agent 选择策略 · 执行计划生成 · 结果整合      │
├─────────────────────────────────────────────────────────┤
│                 执行协调器 (ExecutionCoordinator)          │
│   并行执行调度 · 重试管理 · 状态追踪 · 通道管理            │
├──────────────┬──────────────┬──────────────┬────────────┤
│   Agent A    │   Agent B    │   Agent C    │   Agent D   │
│  (子任务1)    │  (子任务2)    │  (子任务3)    │  (子任务4)   │
└──────────────┴──────────────┴──────────────┴────────────┘
```

- **上级 Agent**：负责任务规划、子任务分配和结果整合
- **下级 Agent**：负责具体执行，通过标准化通信协议交互
- **并行执行**：单个任务可分解为多个子任务并行执行，显著提升效率
- **层级嵌套**：支持至少三层 Agent 嵌套调用，上级协调下级

#### 外围层核心组件

| 组件                       | 类/接口                  | 说明                                                         |
| -------------------------- | ----------------------- | ------------------------------------------------------------ |
| **Agent**                  | `Agent`                 | 核心 Agent 实现，管理任务执行、子 Agent、心跳和状态            |
| **AgentConfig**            | `AgentConfig`           | Agent 配置：最大深度、最大并行数、超时、心跳间隔等              |
| **AgentState**             | `AgentState`            | Agent 运行时状态：状态、负载、任务计数、响应时间等              |
| **TaskQueue**              | `TaskQueue`             | 优先级任务队列，支持任务入队、出队、优先级排序                  |
| **TaskScheduler**          | `TaskScheduler`         | 任务调度器，管理任务执行器、并发控制和事件通知                  |
| **ContextManager**         | `ContextManager`        | 对话上下文管理，参与者管理、状态项、上下文统计                  |
| **ContextWindowManager**   | `ContextWindowManager`  | 上下文窗口管理，窗口类型配置、过期检测、容量管理                |
| **ContextService**         | `ContextService`        | 上下文服务，执行帧栈、上下文传播、过滤查询                      |
| **WorkflowEngine**         | `WorkflowEngine`        | 工作流引擎，管理 Workflow 定义、版本和执行记录                  |
| **WorkflowExecutor**       | `WorkflowExecutor`      | 工作流执行器，基于 DAG 拓扑排序的节点执行                       |
| **OrchestrationLayer**     | `OrchestrationLayer`    | 编排层，任务分解、Agent 选择、执行计划生成                      |
| **ExecutionCoordinator**   | `ExecutionCoordinator`  | 执行协调器，并行执行、重试控制、进度追踪                        |
| **AgentRegistry**          | `AgentRegistry`         | Agent 注册中心，注册/发现、健康检查、负载均衡统计               |
| **AgentChannel**           | `AgentChannel`          | Agent 通信通道，消息订阅、发布、过滤                            |
| **MessageQueue**           | `MessageQueue`          | 优先级消息队列，批量处理、过期清理                              |

#### 设计原则

- **高度灵活**：外围模块可替换、可扩展、可自定义
- **可扩展**：新 Agent / Provider / 任务可直接插入外围层
- **可自定义**：策略、路由规则、任务模板均可配置

#### 约束

- AI Router 仅做策略决策，不直接执行高频操作
- 外围层通过内核层接口执行底层操作，不绕过内核层
- 外围层模块间通过标准化协议通信，禁止直接耦合

### 2.3 自定义层（Customization Layer）

#### 职责

为用户和开发者提供扩展和定制能力，是系统与最终用户的交互入口。自定义层允许用户添加新模块、定义新策略、接入新 Provider，而不修改内核层和外围层的核心代码。

#### 核心功能清单

| 功能                    | 说明               | 关键特性                |
| ----------------------- | ------------------ | ----------------------- |
| 添加新模块              | 自定义功能模块开发 | 插件机制、动态加载      |
| 定义新策略              | 自定义调度策略     | 策略注册、配置驱动      |
| 接入新 Provider         | 自定义 AI 模型接入 | Provider 接口、统一抽象 |
| 定义 CLI 命令           | 自定义命令行操作   | 命令注册、参数定义      |
| 管道式组合任务          | 自定义任务流程编排 | 流式管道、模块组合      |

#### 设计原则

- **插件机制**：所有自定义功能通过插件系统接入
- **社区可贡献**：自定义模块可独立开发和分发
- **配置驱动**：自定义行为通过配置文件定义，无需编码

#### 约束

- 自定义内容不得破坏内核层稳定性
- 自定义模块必须遵循插件接口规范
- 自定义层不得直接访问内核层内部实现

## 第三章：层间交互规范

### 3.1 层间数据流向

三层架构的层间数据流遵循严格的单向依赖和双向通信原则：

```
自定义层 ──注册/配置──→ 外围层 ──指令/参数──→ 内核层
   ↑                       ↑                       │
   │                       │                       │
   └──扩展点/插件接口──────┘──状态/事件/结果──────┘
```

#### 内核层 → 外围层

- **状态反馈**：内核层将执行状态实时上报给外围层
- **执行结果上报**：操作完成后将结果传递给外围层
- **事件通知**：内核层通过 EventBus 发布状态变更事件

#### 外围层 → 内核层

- **指令下发**：外围层通过内核层接口下发操作指令
- **参数配置**：外围层向内核层传递配置参数
- **模块调用**：外围层调用内核层暴露的功能接口（如 `text`、`info` 服务）

#### 外围层 → 自定义层

- **扩展点暴露**：外围层定义可扩展的接口和钩子
- **插件接口**：外围层提供标准化的插件加载和注册接口
- **配置注入**：外围层将运行时配置注入自定义层

#### 自定义层 → 外围层

- **策略注册**：自定义层向 Agent 系统注册新策略
- **Provider 注册**：自定义层注册新的 AI 模型 Provider
- **命令注册**：自定义层注册新的 CLI 命令

### 3.2 通信格式

层间通信统一使用以下格式：

| 通信方式     | 适用场景             | 格式                                     |
| ------------ | -------------------- | ---------------------------------------- |
| JSON         | 结构化数据传递       | 标准 JSON 对象，包含 type/payload/timestamp |
| 文件         | 大数据量和持久化场景 | 标准文件 I/O，支持流式读写                |
| stdin/stdout | 管道式组合           | 纯文本流，支持管道操作符连接             |
| 事件总线     | 实时状态同步         | 发布-订阅模式，异步非阻塞                |

### 3.3 状态同步机制

内核层的输出状态需实时供外围层使用，采用以下同步机制：

- **事件总线（EventBus）**：内核层通过 EventBus 发布状态变更事件，外围层订阅感兴趣的事件
- **消息队列（MessageQueue）**：高频状态更新使用消息队列缓冲，避免阻塞
- **共享存储（ContextService）**：跨层状态通过上下文服务持久化，确保数据一致性

## 第四章：Agent 并行多层架构

### 4.1 架构概述

并行多层 Agent 架构是系统的核心调度引擎，采用层级式设计理念实现复杂任务的智能分解和协同处理。上级 Agent 负责任务规划、子任务分配和结果整合，下级 Agent 负责具体执行，两者通过标准化通信协议进行交互。

### 4.2 三层 Agent 结构

| 层级       | 组件                     | 职责                             |
| ---------- | ------------------------ | -------------------------------- |
| 编排层     | OrchestrationLayer       | 任务分解、Agent 选择策略、计划生成 |
| 协调层     | ExecutionCoordinator     | 并行执行调度、重试管理、状态追踪   |
| 执行层     | Agent + TaskScheduler    | 承载具体业务逻辑执行               |

### 4.3 核心能力

1. **任务分解引擎**
   - 支持将复杂任务自动拆解为可执行的子任务
   - 识别任务间的依赖关系并排序
   - 支持条件分支和循环结构

2. **Agent 调度器**
   - 管理 Agent 实例的创建、销毁和状态监控（AgentRegistry）
   - 负载均衡策略分配任务
   - 支持任务优先级队列（TaskQueue）

3. **并行执行**
   - 单个任务可分解为多个子任务并行执行
   - 执行协调器（ExecutionCoordinator）管理并行度和重试
   - 支持最多 10 个并行子任务

4. **结果整合**
   - 收集各子任务执行结果（OrchestrationLayer）
   - 处理部分成功/失败场景
   - 生成最终执行报告

5. **Agent 注册中心**
   - 动态注册和发现 Agent 服务（AgentRegistry）
   - 心跳检测和健康检查
   - 故障自动转移

### 4.4 通信机制

- Agent 间通信采用**发布-订阅模式**（AgentChannel + MessageQueue）
- 支持**同步和异步**两种调用方式
- 状态同步通过**上下文服务（ContextService）**实现，确保多 Agent 环境下数据一致性
- 消息格式采用标准化 JSON 协议，包含 message_id、source、target、action、payload、timestamp

### 4.5 配置项

| 配置项                | 默认值 | 说明              |
| --------------------- | ------ | ----------------- |
| max_agent_depth       | 3      | 最大 Agent 嵌套层级 |
| max_parallel_tasks    | 10     | 最大并行任务数    |
| communication_timeout | 5000   | 通信超时时间(ms)  |
| heartbeat_interval    | 30     | 心跳间隔(秒)      |

## 第五章：架构优势与挑战

### 5.1 设计优势

| 优势                     | 说明                                                                     |
| ------------------------ | ------------------------------------------------------------------------ |
| **稳定性**               | 核心内核层独立运行，高频操作不依赖 AI 推理，确保底层功能的可靠性和低延迟 |
| **灵活性**               | 外围模块化层可替换/扩展，Agent 策略可配置，Provider 可切换               |
| **可扩展性**             | 新模块/Provider/任务可直接插入外围层，无需修改内核层代码                 |
| **自定义便捷**           | CLI 用户可组合模块快速实现复杂自动化，插件机制降低扩展门槛               |
| **并行高效**             | 并行多层 Agent 架构充分利用计算资源，显著缩短任务执行时间                |
| **符合 Unix/Linux 哲学** | 内核稳定 + 外围灵活 + 一切皆可组合，管道式操作和流式处理                 |

### 5.2 潜在挑战与解决思路

| 挑战                       | 问题描述                                            | 解决思路                                                                |
| -------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------- |
| **模块接口规范**           | 内核模块接口和外围模块通信格式需要统一标准          | 制定统一的接口规范（JSON/文件/stdin-stdout），定义标准化的请求-响应协议 |
| **状态同步**               | 内核层输出状态需实时供 Agent 使用，存在延迟风险     | 采用 EventBus + MessageQueue 机制，确保状态变更的实时传播和缓冲         |
| **高频任务与 AI 决策冲突** | 高频操作需要低延迟，而 AI 推理可能引入延迟          | 高频操作直接在内核层执行，Agent 仅做策略决策，两者解耦                  |
| **多 Agent 协同**          | 多个 Agent 并行执行需要协调和状态一致性             | 通过 ExecutionCoordinator + ContextService 实现分布式协调和状态同步     |
| **多 Provider 管理**       | 多个 AI Provider 需要统一管理和灵活切换             | 外围层抽象 Provider 接口，保证切换灵活且调用方式统一                    |

| 包名               | 架构角色     | 职责                                                     | 依赖层级 |
| ------------------ | ------------ | -------------------------------------------------------- | -------- |
| `@organic/ui`      | 自定义层入口 | CLI 界面、用户交互、命令定义、管道式任务组合界面         | Level 4  |
| `@organic/storage` | 自定义层支撑 | 状态持久化、配置存储、多后端存储（Memory/File/Database） | Level 2  |

### 6.4 跨层包说明

`@organic/plugins` 跨越外围层和自定义层：

- **外围层角色**：定义插件接口规范、管理插件生命周期、提供插件加载和注册机制
- **自定义层角色**：作为自定义功能的扩展通道，桥接外围层与自定义层，允许用户通过插件机制注册新模块、新 Provider 和新策略

这种跨层设计使得插件系统既是外围层的扩展骨架，又是自定义层的接入通道，实现了"一次定义、双向服务"的效果。

### 6.5 包间依赖关系

```
         @organic/utils (Level 0 - 基础层)
                ↑
         @organic/kernel (Level 1 - 内核层)
           ↗       ↖
  @organic/plugins  @organic/tools (Level 2 - 外围层)
      ↖                ↗
       @organic/agent (Level 3 - 外围层核心)
              ↑
         @organic/ui (Level 4 - 自定义层入口)
```

关键依赖链路：

- `@organic/kernel` ← `@organic/agent`（agent 调用 kernel 执行底层操作）
- `@organic/kernel` ← `@organic/tools`（tools 调用 kernel 执行工具操作）
- `@organic/kernel` ← `@organic/utils`（kernel 依赖 utils 的基础设施）
- `@organic/agent` ← `@organic/plugins`（agent 通过 plugins 加载和调度模块）
- `@organic/agent` ← `@organic/storage`（agent 通过 storage 持久化状态）
- `@organic/plugins` ← `@organic/storage`（plugins 通过 storage 持久化配置）
- `@organic/tools` ← `@organic/plugins`（tools 通过 plugins 注册和发现工具）
- `@organic/ui` ← `@organic/agent`（ui 通过 agent 调度任务）
- `@organic/ui` ← `@organic/tools`（ui 通过 tools 执行操作）

## 第七章：实践建议与 MVP 路径

### 7.1 分层开发策略

| 层级     | 开发节奏                        | 更新频率 | 说明                       |
| -------- | ------------------------------- | -------- | -------------------------- |
| 内核层   | 稳定基础，低频更新              | 低       | API 一旦发布需保持向后兼容 |
| 外围层   | Agent 调度 + Provider 可频繁迭代 | 中-高    | 策略和 Provider 可独立迭代 |
| 自定义层 | CLI 命令和用户任务模板          | 高       | 用户可自由扩展和定制       |

### 7.2 模块化接口设计

- **统一 I/O 格式**：所有模块间通信使用 JSON/文件/stdout 标准格式
- **流式管道组合**：支持模块间管道式数据流，类似 Unix 管道操作符
- **接口版本管理**：内核层接口采用语义化版本，确保兼容性

### 7.3 反馈循环机制

```
内核层执行操作 → 状态反馈 → 外围层 Agent 决策 → 指令下发 → 内核层执行
     ↑                                                          │
     └────────── 外围层更新全局状态 ←─── ContextService 持久化 ───┘
```

- 内核层执行结果通过 EventBus 反馈给外围层
- Agent 根据反馈做出策略决策，驱动下一模块
- 外围层更新全局状态，通过 ContextService 持久化

### 7.4 可扩展性策略

- **新模块**：通过插件机制动态加载，无需修改核心代码
- **新 AI Provider**：实现 Provider 接口，注册到 Agent 系统
- **新 Agent**：实现 Agent 接口，注册到 AgentRegistry
- **新任务模板**：定义任务描述和编排规则，注册到工作流引擎
- **新 CLI 命令**：实现命令接口，注册到 CLI 系统

### 7.5 MVP 建议

**先开发核心内核 + Agent 原型**，再逐步扩展：

1. **Phase 1 - 内核 MVP**：实现 `@organic/kernel` 核心功能（Kernel、EventBus、LifecycleManager、PluginManager、TextService、InfoService）+ `@organic/utils` 基础设施
2. **Phase 2 - Agent 原型**：实现 `@organic/agent` 基础调度（Agent、TaskQueue、TaskScheduler、ContextManager）+ `@organic/plugins` 插件加载 + 单个 Provider
3. **Phase 3 - 编排能力**：实现工作流引擎（WorkflowEngine、WorkflowExecutor）+ 编排层（OrchestrationLayer、ExecutionCoordinator）+ Agent 注册中心（AgentRegistry）
4. **Phase 4 - 工具链完善**：实现 `@organic/tools` 工具系统 + `@organic/storage` 存储系统
5. **Phase 5 - 用户入口**：实现 `@organic/ui` CLI 界面 + 命令系统
6. **Phase 6 - 生态扩展**：多 Provider 支持、社区插件、高级策略

## 总结

Organic-Interface 的三层架构设计——**内核层 + 外围模块化交互层 + 自定义层**——实现了**稳定 + 灵活 + 可扩展**的架构目标，适合多模态自动化 AI CLI 场景，完全符合 Unix/Linux 哲学。

内核层以 **Kernel** 为核心，整合 **EventBus**（事件驱动通信）、**LifecycleManager**（生命周期状态机）、**PluginManager**（插件加载/注册）、**TextService**（CLI 文本输出）和 **InfoService**（系统/运行时信息），提供稳定可靠的底层能力。

外围层以 **并行多层 Agent 架构**为核心，通过 **Agent + TaskScheduler**（任务调度）、**ContextManager + ContextService**（上下文管理）、**WorkflowEngine + WorkflowExecutor**（工作流引擎）、**OrchestrationLayer + ExecutionCoordinator**（编排协调）、**AgentRegistry**（注册中心）和 **AgentChannel + MessageQueue**（通信）等组件，实现复杂任务的智能分解、并行执行和协同处理。

7 个包与三层架构的映射关系清晰明确：内核层（kernel + utils）提供稳定基石，外围层（agent + plugins + tools）提供灵活交互，自定义层（ui + storage）提供用户定制能力。其中 `@organic/plugins` 跨层设计，桥接外围层与自定义层，是系统扩展性的关键。

**关键建议**：先开发 MVP 核心内核 + Agent 原型，验证架构可行性后再逐步扩展编排层和自定义层功能。
